# Web Push backend and frontend contract

The **computer's connector**, not the public relay, observes native Core events and sends Web Push over outbound HTTPS. Its process-lifetime Core subscription runs even with zero browser/WebRTC sessions. Run the connector continuously; neither the public website nor a remembered browser connection can observe an offline connector. All native Core terminals visible to that connector are covered, including remembered computers that are not currently selected in a browser. Only root structured OSC 7501 status transitions into `done`, `blocked`, and `error` notify; terminal output and process exit are not interpreted as completion.

## Authenticated API

These paths use normal local authenticated/exact-Origin HTTP protections, or the existing authenticated encrypted peer control transport. They are NOT public relay endpoints. Peer registrations are bound server-side to the verified browser signing public key, not a caller-supplied owner. Local HTTP binds registrations to the server-derived hashed cookie identity (or hashed bearer identity); it never accepts an owner supplied by a request. Cookie profiles do not share a fallback owner.

Access-token rotation retains only the initiating profile/key's registrations, cancels other owners' queued and in-flight delivery, and removes their foreground leases. Enrollment is serialized with rotation and rechecks authentication after waiting. Startup reconciles the push file against the authoritative durable Auth/Pairings allowlist **before** observing Core, so a failed cleanup after committed revocation cannot restore stale subscriptions on restart. Unattributable legacy `local` registrations are removed; that browser may need to enable notifications again.

* `GET /api/notifications`: `{supported:true,publicKey:"<unpadded base64url P-256 public key>"}`; `{supported:false}` on backends without an observer.
* `POST /api/notifications`: `{subscription:{endpoint,keys:{p256dh,auth}},connectionId,channel:"stable"|"main"}`. Returns `{ok:true}`. Registration is idempotent for the authenticated device and endpoint. Browser subscription JSON's optional expirationTime is accepted and ignored. `connectionId` is the secret-free computer route identifier, at most 128 ASCII letters/digits/underscore/hyphen.
* `POST /api/notifications/delete`: `{endpoint}`. Returns `{ok:true}`. Removes only this authenticated device's registration from this connector. Repeat is safe.
* `POST /api/notifications/seen`: `{endpoint,terminal,clientId,pageVisible?}`. Returns `{ok:true}` for a registered endpoint. A visible, connected page refreshes `pageVisible:true` every 10 seconds: this silences **all terminals for that device’s subscription**, because the ready-agent badge handles in-app attention. Keyboard/window focus is not required. Hidden pages send empty `terminal` without `pageVisible` to release their own lease. Leases expire after 30 seconds without a heartbeat, using monotonic time; no durable read receipt or historical queue is created. `clientId` is a random per-page identifier (1–128 ASCII letters/digits/underscore/hyphen); another visible tab keeps its own independent lease. Other devices, computers and channels are unaffected. Omitted/false `pageVisible` retains legacy same-terminal suppression; empty `terminal` then clears only that client’s lease. The connector checks leases before queueing and starting delivery. The service worker also guards in-flight pushes when an exact same-computer/channel page is visible. Older strict connectors receive legacy presence after a 422 response; foreground suppression then relies on the worker. Abrupt suspension/disconnect may leave a lease until expiry.

Error bodies use the existing API error envelope. Bad subscriptions, unsupported provider endpoints, invalid destinations or capacity exhaustion return 400. Authentication/Origin enforcement is unchanged. Persistence failures are reported, never logged with request material.

VAPID keys are **per connector state directory**. A service worker PushSubscription is bound to one applicationServerKey. Use a per-computer push-only worker registration (for example script `/main/sw.js`, scope `/main/notifications/<connectionId>/`), separate from the app shell registration. Derive release channel from the script URL, not the push-only scope. Do not reuse one connector's subscription/key for another computer. Unregister/delete the intended backend registration before browser unsubscribe. Disabling a target while offline cannot revoke its backend until it reconnects; browser unsubscribe invalidates the endpoint independently.

## Encrypted payload

```json
{"version":1,"eventId":"<UUID>","kind":"done","connectionId":"<public computer ID>","channel":"stable","terminal":"<native terminal address>"}
```

`kind` is `done`, `blocked`, or `error`. The worker must validate all fields, build only a same-origin channel connection route, and route to the native address after normal authentication. No access token, prompt, command, title, terminal text or private URL is included. Use generic lock-screen wording: “Agent finished”, “Agent needs input”, “Agent reported an error”. Native terminal addresses are intentionally included solely as routing identifiers; do not render them as lock-screen labels. Destinations may be stale/missing and must degrade gracefully. Never open the keyboard automatically.

## State, deduplication and failure policy

`web-push/notifications-key.json` contains the private VAPID scalar; `notifications.json` contains subscriptions/auth secrets and terminal transition baselines. Existing owner-only state helpers enforce 0700 directories, 0600 single-link files, no symlink paths, atomic replacement, file and parent fsync. An exclusive process lock prevents concurrent writers. Keep these files private and include them in protected backups. At connector startup registrations for browser keys no longer paired are purged, including after `--reset-pairings`. Deleting/rotating the VAPID key requires browser unsubscribe and re-registration; copying the key alone without subscriptions does not restore delivery. Never publish these files or logs containing their contents.

Initial snapshots, Core reconnect snapshots, and missed-event replacements **seed baselines without notifying**. Repeated statuses and other event kinds do not notify. Every consumed transition is durably persisted before any network send. Restarts do not replay historical statuses. This is an intentional **at-most-once attempt** policy: a crash after persistence but before send, network ambiguity, observer overflow, and prolonged overload may lose a notification. There is no retry queue and no retry-driven duplication. Network delivery is separate from observation: at most eight sends run concurrently and at most 512 additional per-subscription deliveries wait in memory. Queue overflow drops new deliveries after committing consumption; queued deliveries older than five minutes are dropped, and in-flight sends are bounded by the same maximum age. Closing the observation sender drains queued deliveries; cancellation aborts in-flight child tasks. A lagged observer, baseline capacity failure (4096 currently live terminals), or baseline persistence error discards buffered observations and requests a fresh snapshot. The single Core monitor publisher sends that snapshot after its next message, including a heartbeat, instead of forwarding that message as a live transition. Only subsequent live transitions can notify; recovery never replays missed statuses. Persistent storage/capacity failures keep requesting snapshots without notifying until safe recovery. Native terminal removal prunes its baseline, so lifetime terminal churn does not consume capacity. HTTP 404/410 removes expired endpoints; other failures get no retry (zero is the bounded retry policy). TTL is five minutes. Push services/OSs can still delay, coalesce, duplicate or drop messages: the worker should use eventId as a notification tag. Exactly-once end-to-end delivery is not promised.

## Network/security and limitations

The connector needs DNS plus outbound TCP 443 to `fcm.googleapis.com` (Chromium/Android), `updates.push.services.mozilla.com` (Firefox), and `web.push.apple.com` (Apple). Only these exact hosts are accepted; arbitrary/custom push providers are explicitly unsupported, including unverified regional provider hostnames. Requests require HTTPS/default port, no URL credentials/fragment. DNS answers are checked for public addresses on every send and pinned into the HTTP client. Proxy environment variables and redirects are disabled. This prevents arbitrary endpoint, redirect and DNS-rebinding SSRF; endpoint/auth secrets never reach the relay. Standard `web-push` RFC 8291/8188 aes128gcm encryption and RFC 8292 VAPID signatures are used. The VAPID contact claim is the public project URL.

Local mode also starts a persistent observer using a `web-push` directory beside its token file, but the current frontend notification setup requires a relay `/connections/<id>` context: **local-mode end-to-end notification opt-in/click routing is not supported by the current UI**. The backend API is present for future secure local connection routing, not a claim of working local notification setup. Browser push APIs still require a trusted secure context. Plain LAN HTTP is not made push-capable by this backend. A private Core does not require inbound exposure: its connector sends outbound directly to browser push services. Delivery stops when that computer/connector is asleep/offline. Browser permission/OS Focus/power restrictions remain independent of app preference and endpoint health.

The connector state distinguishes terminal subscription readiness from layout metadata readiness: `metadataReady` starts false, resets on each fresh event subscription, and becomes true only after machine/document refresh completes for that subscription. Notification click targets should wait for both connectivity and metadata readiness before resolving a pane; an older refresh completing across reconnect must not mark the new session ready.

Physical Android/iOS background delivery, subscription renewal, and vendor-specific behavior require real-device verification; unit tests and browser emulation do not prove them. No end-to-end physical-device delivery has been verified by this implementation.
